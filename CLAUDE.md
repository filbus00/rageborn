# Project overview

Rageborn: isometric Diablo-style action RPG for iOS. Unity 6000.6.2f1, URP 2D renderer, new Input System only (`activeInputHandler: 1`, so never use `UnityEngine.Input`).

The design docs in `Docs/` are the source of truth for design decisions. Start at `Docs/00-vision-and-scope.md`. If code and docs disagree, ask before changing either.

- 2D isometric sprites: Isometric `Grid`/`Tilemap` for the world, sprite characters.
- Portrait only, iPhone only (no iPad in 1.0), iOS 16+, target 60 fps (`GameBootstrap`). No online features in 1.0 (no Game Center or leaderboards); iCloud save sync only.
- One-thumb control: a floating stick is the only input. Attacks and skills fire automatically, so there are no skill buttons, no tap-to-move and no dodge button.
- Company Filbus Software, bundle ID `com.filipbusic.rageborn`.
- Diablo 1 structure, not a survivor game: the player starts in a safe walkable town and descends a dungeon level by level by stairs. Enemies are packs placed in rooms that idle until aggro, and they never spawn around the player. See `Docs/00-vision-and-scope.md` and `Docs/05-world-and-content.md`.

# Layout

- `Assets/_Project/` holds all game content. `Assets/Settings/` (URP and input assets) comes from the Unity template.
- `Scripts/Runtime` is the `ARPG.Runtime` assembly (namespace `ARPG`), `Scripts/Editor` is `ARPG.Editor`.
- Physics/sorting layer names live in `GameLayers.cs`. `Tools > ARPG > Apply Project Setup` (`ProjectSetup.cs`) creates them in TagManager and applies iOS, identity and sorting settings. It is idempotent. Keep the two files in sync.
- `Scenes/Sandbox.unity` is the dev scene (built by `Tools > ARPG > Create Sandbox Scene`, which rebuilds the Grid if you run it again): isometric Grid (cell 1 x 0.5) with a `Ground` Tilemap of generated placeholder tiles and a portrait-framed camera (orthographic size 8). Replace the tiles with real art later.

# Isometric conventions

- Tile art is 128x64 px diamonds at 128 pixels per unit (1 x 0.5 world units per cell).
- Transparency sort mode is Custom Axis (0,1,0): lower Y draws in front. Sprite pivots must be at the feet.
- Characters and props use the `Entities` sorting layer so they Y-sort against each other.
- Gameplay ranges are in ground space (1 unit = one tile width). Stick input is unprojected from screen space (screen Y doubled) before moving characters. See `Docs/01-core-gameplay.md`.
- No NavMesh in 2D. Enemy navigation is a grid pathfinder over the tilemap.
- In ground space the tile lattice is a square grid rotated 45 degrees: an edge neighbour is 0.707 away, a corner neighbour 1.0. `IsoMath.CellToGround`/`GroundToCell` convert (they assume the Grid sits at the world origin).

# Player, input and camera

- `StickMath` (pure) and `FloatingStickInput` (Enhanced Touch, mouse-simulated in the editor) produce a screen-space stick value. `PlayerController` converts it to ground space with `IsoMath` and drives a `Rigidbody2D`. `FollowCamera` follows with the lead and framing from the docs. `StickVisual` draws the stick on an overlay canvas.
- `FloatingStickInput` ignores a touch that begins over a UI element (`EventSystem.IsPointerOverGameObject`), so a tap on an inventory-screen button inside the stick's touch zone starts that button, not the stick underneath it.
- `Tools > ARPG > Add Player And Camera To Sandbox` generates the placeholder art, the `Player` prefab and the scene wiring. It rebuilds the Player, Stick Input and Stick Canvas objects if run again.
- Components find each other at runtime (`FindAnyObjectByType`) when their reference fields are empty.
- EditMode tests are in `Assets/_Project/Tests/EditMode`. The pure math (`StickMath`, `IsoMath`) has no Unity scene dependency.

# Enemies

- Enemies are placed as packs, never spawned around the player (see the structure note above). `EnemyPack` (3 to 12 members) spawns its members from the pool around its position when the level loads. Members idle at their home spot until the player is within aggro range, chase, and after the leash breaks (beyond 20 units for 4 s) walk home and idle again (`EnemyState.Return`). Killed enemies stay dead: a pack never respawns a member and counts `KilledCount` (per-level saving of that state is not built yet).
- `EnemyManager` owns the pool and everything enemies share: a `NavGrid` baked by `NavGridBaker` (a cell is walkable when the Ground tilemap has a tile and no tilemap on the Obstacle layer does), a `FlowField` (one Dijkstra from the player's cell, not A* per enemy) and a `SpatialHash` of enemy positions. It ticks every `EnemyController` once per frame, so enemies have no `Update`. Each pack builds a lazy flow field to its own center so returning enemies route around walls.
- Enemies have no Rigidbody or collider. They live in ground space and only the transform is projected with `IsoMath`. Find neighbours and targets through the spatial hash. A wall is one cell thick (0.707), so `EnemyController.Move` splits long steps into pieces of 0.25 or less; without that, a frame hitch let an enemy jump a wall. Keep the per-frame path allocation free: over 6000 update triples of an unbroken fight (manager, combat and loot) the heap did not grow, and the manager's `Update` took 0.02 to 0.07 ms with 40 enemies, both in the editor and not on a phone. See the note on measuring allocations under Notes.
- `EnemyDefinition` (ScriptableObject) holds the tuning. Its values marked as tuning are not in the docs yet. States are Idle, Approach, Attack (a 0.35 s wind-up during which the enemy swells as a tell, then the hit lands if the player is still within reach plus 0.3), Recover (0.65 s), Return and Dead (a short fade, then back to the pool). The swarmer's attack numbers are tuning values, since the docs give none; a level 1 hit is 3 damage from the docs' curve. `TakeDamage(float)` takes damage that has already been through the hit formula, and a hit wakes an idle or returning enemy.
- Walls are a `Walls` Tilemap on the Obstacle layer (Individual render mode so they Y-sort against characters, Grid collider type, merged into one static collider for the player).
- `Tools > ARPG > Add Enemies To Sandbox` builds the swarmer prefab, the definition (`Data/Enemies/Swarmer.asset`) and the Enemy Manager. `Tools > ARPG > Add Test Room To Sandbox` builds a walled room with a divider that has a two cell gap, four packs of 10 and the player start. Run it after `Create Sandbox Scene` rebuilds the Grid, which removes the walls. Rerunning either keeps the tuned definition.
- The pure classes (`NavGrid`, `FlowField`, `SpatialHash`, the pack slot layout) and `NavGridBaker` are covered by EditMode tests. Enemy behaviour was checked in play mode by script (aggro, routing through the gap, leash and return, wall tunneling); there are no PlayMode tests yet.

# Combat

- The simulation math is pure and tested: `CombatFormulas` (the base curves and the hit formula from `Docs/03-itemization.md`: weapon damage, enemy life, armor reduction with its 80 percent cap, increased and more multipliers, crits), `FocusPool` (0 to 100, regen 6 per second) and `SweepGeometry` (sweep containment and target choice).
- `PlayerCombat` lives on a `Player Combat` scene object and finds the player and the enemy manager at runtime, so rebuilding the player does not remove it. Every frame it picks the target (nearest enemy in reach inside the 200 degree forward cone, else nearest in reach), swings the basic attack at 1.4 per second (120 degree sweep, reach 2.0) and auto-casts skills in slot order when the 0.35 s global cast timer is free, the skill is off cooldown, its Focus is paid and a target is in reach. There is no input. It runs in Update; the docs call for a fixed timestep, which is not done yet.
- `SkillDefinition` (ScriptableObject) holds a sweep skill's numbers. The one skill is **Cleave** from the Warden draft, a placeholder until the Wrathborn's skills are designed (`Docs/08-production.md`, open question 8).
- Choices the docs leave open, made here: Focus is gained once per basic swing that hits (not per enemy), a fresh character starts with full Focus, and the basic attack and skills run on independent timers.
- Enemies get their queries from `EnemyManager.QueryEnemies`, which reads the same spatial hash. `EnemyManager` runs first (`DefaultExecutionOrder(-100)`).
- The slash wedges (`SweepEffect`) live under a parent scaled to half height, so effects are positioned and rotated in ground space.
- `Tools > ARPG > Add Combat To Sandbox` builds the wedge art, `Data/Skills/Cleave.asset` and the `Player Combat` object. Scene build order: Create Sandbox Scene, Add Player And Camera, Add Enemies, Add Test Room, Add Combat.
- Not built yet: damage numbers, hit stop, drops, potions, dodge, the global cast timer with more than one skill.

# Survival, town and session

- `PlayerHealth` (on the `Player Vitals` object, with `DeathFlow`) holds a `LifePool`, applies armor and raises `Died`. Both `Armor` and `MaxLife` read live from `GameSession.Current.Equipment` (see Loot); `PlayerHealth` rescales the `LifePool`'s max, keeping the current fraction, whenever `GameSession.Changed` fires, so equipping more life updates without a scene reload. Life is carried between scenes in `GameSession`, so stairs do not heal. There are no potions or regeneration yet (besides the Life on Hit affix), so life only goes down until death otherwise.
- `GameSession` (pure, tested) is everything that must survive a scene change within one game session: equipped gear, the backpack, gold, corpses, which pack members were killed, life and the loot roller (so its bad-luck counter survives). `GameSession.Current` is replaced at the start of every play (`RuntimeInitializeOnLoadMethod`), because the project runs with domain reload off and statics would otherwise leak between editor plays. A future sleep mechanic resets it; saving to disk builds on it.
- Death (`DeathFlow`): the character stops, its equipped gear becomes a `Corpse` at the death spot, and the screen fades to the `Town` scene. Only equipped gear is left; a death with nothing equipped makes no corpse and leaves the first one where it is. Corpses never expire. `CorpseSpawner` places a `CorpseMarker` for each corpse of the current scene, and walking onto it picks the gear back up. A character with no weapon fights unarmed, valued by the weapon curve at item level 0 (damage 6). Weapon, Chest and Helm exist as gear (see Loot).
- Killed enemies stay dead: `EnemyPack` records each kill by scene name, pack object name and slot in `GameSession`, and skips those slots when the level loads again. Pack object names must therefore be unique within a scene.
- Stairways are `SceneExit` triggers (walk onto them, no button) that fade and load a scene by name; they wait 0.75 s after the scene starts so arriving next to one does not bounce the player. The player arrives wherever the target scene placed it. The two scenes in the build settings, Town then Sandbox, are referenced by name in `DeathFlow` and the stairways.
- The HUD is a life bar (`LifeBar`) and a black fade overlay (`ScreenFade`) on two overlay canvases.
- `Tools > ARPG > Add Survival To Sandbox` builds the HUD, the vitals object, the corpse spawner and the stairway up. `Tools > ARPG > Create Town Scene` copies the sandbox to `Scenes/Town.unity` and strips it of enemies, combat and walls, leaving the ground, the player, the HUD and a stairway down, and writes the build settings. Build order: Create Sandbox Scene, Add Player And Camera, Add Enemies, Add Test Room, Add Combat, Add Survival, Create Town Scene. Rebuilding the sandbox means rerunning the later steps.
- The town has no NPCs yet. The Portal Tome, waypoints and the Waystone are not built.

# Loot

- Items are pure data (`Item`: slot, rarity, item level, affixes). Three slots exist so far: Weapon, Chest, Helm (`ItemSlot`; the other seven in the docs are added as items for them exist). A weapon's damage and an armor piece's protection come from item level alone (`WeaponAverageDamage`, `ArmorValue`); affixes add on top.
- `Affix`/`AffixTable`/`AffixRoller` (pure, tested): a curated slice of the roughly 90 affixes in `Docs/03-itemization.md` — 4 prefixes (flat weapon damage, increased damage, life, armor) and 5 suffixes (attack speed, critical chance, critical damage, life on hit, cooldown reduction), each with 5 tiers gated by item level (T5 unlocks at level 1, T1 at level 60) and a value rolled uniformly within the tier's scaled range. Affix counts by rarity follow the docs (Common 0, Magic 1 and 1, Rare and Legendary 2 to 3 of each), capped by how many of that kind a slot has eligible: Weapon has 2 prefixes and 4 suffixes eligible, Chest and Helm both have 2 prefixes (Life, Armor), and only Helm has an eligible suffix (Cooldown Reduction) so far. Legendary reuses Rare's affix range; fixed legendary affixes and unique powers are not built.
- `LootRoller` (pure, seeded, tested) follows `Docs/03-itemization.md`: a normal enemy drops an item 6 percent of the time, rarity weights 60, 30, 8.5 and 1.5, Magic Find multiplies the top three, and the legendary weight doubles after 300 kills without one and triples after 600 (every kill counts). A drop's slot is chosen uniformly among the three that exist; there is no per-slot drop table yet. Gold is `0.6 * level^1.3` rounded, with a floor of 1. Item level equals the enemy's level. The live session seeds its roller from the clock; pass a seed to replay.
- `EquipmentState` (in `GameSession.cs`) holds one item per slot, immutable (`With` returns a changed copy). It sums each affix-derived stat across every equipped item (`TotalArmor`, `TotalLifeBonus`, `FlatWeaponDamageBonus`, `IncreasedDamagePercent`, `AttackSpeedPercent`, `CriticalChancePercent`, `CriticalDamagePercent`, `LifeOnHit`, `CooldownReductionPercent`), so a future slot or affix granting the same stat just adds in. `PlayerHealth` and `PlayerCombat` (damage, attack speed, the crit roll, life on hit healing, cooldown reduction) read these live every use, not cached.
- `GameSession.PickUp` only bags a found item now; nothing is auto-equipped. Equipping is the player's choice from the inventory screen (`EquipFromInventory`, `Unequip`, `Discard`, all pure and tested). `Retrieve` (walking onto your own corpse) still restores gear automatically, slot by slot as one all-or-nothing transaction, using a rough item-level-then-rarity comparison in place of the docs' power score (which needs a DPS/effective-life model this project does not have yet).
- `LootDirector` (on a `Loot System` object) listens to `EnemyManager.Killed`, rolls gold and an item and places them from a pool of drop objects. `DropItem` and `DropGold` are public for chests, elites and bosses later. Drops still on the ground are lost when the scene changes.
- `LootDrop` draws a floor marker and, for items, a beam whose color and height follow rarity (colors from `Docs/06-ui-ux.md`, heights are tuning values).
- Auto-loot (`PlayerLoot`, rules in the pure `AutoLootRules`): everything within 2.5 units; gold always, items only when the character has not been hit for 1.5 s or nothing is engaged with it. An item stays on the ground if the 40 slot `Inventory` is full.
- `InventoryScreen` is the equip screen (`Docs/08-production.md`: no separate pause menu, just this). A "Bag" button on the HUD opens a full-screen panel with the three equipped slots (tap one to unequip), a stats readout and the scrollable backpack, each row with Equip and Discard. Opening it sets `Time.timeScale = 0`, the game's only pause; closing restores it. Rows are built procedurally at runtime, not from a prefab; the backpack list detaches children before `Destroy` (which is deferred to end of frame), so two refreshes inside one frame don't stack rows. Replaced and deleted the placeholder `LootHud` text readout.
- `Tools > ARPG > Add Inventory Screen To Sandbox` builds the Bag button and the inventory canvas; run after Add Loot To Sandbox. It also adds the scene's only `EventSystem` (`InputSystemUIInputModule`, not the legacy module) and a `GraphicRaycaster` on the HUD canvas if missing — nothing before this screen had real UI buttons to click, so neither existed; verified with a raycast at the Bag button's screen position, not just calling `onClick` directly (which proves nothing about real input reaching it). Build order is now: Create Sandbox Scene, Add Player And Camera, Add Enemies, Add Test Room, Add Combat, Add Survival, Add Loot, Add Inventory Screen, Create Town Scene.
- Not built yet: the other seven slots, the rest of the affix pool (resistances, dodge, gear Magic Find, sockets and gems), fixed legendary affixes and unique powers, the loot filter, real salvage materials (Discard just removes the item, nothing is returned), elite/boss/chest sources, keeping drops across scene changes, pickup and drop sounds, item tooltips.

# Notes

- Measuring allocations in the editor: `GC.GetAllocatedBytesForCurrentThread()` always returns 0 here, even for a 100 KB array, so it proves nothing. `Profiler.GetMonoUsedSizeLong()` and `GC.GetTotalMemory(false)` work but move in blocks of about 4 KB, so use them over thousands of iterations (compare against a control loop) and first check that they detect an allocation you know you made. An earlier version of these notes claimed "0 bytes" from the dead counter.
- Unity holds a lock on the project while the editor is open. Do not hand-edit `ProjectSettings/*.asset` then; apply settings through editor scripts instead.
