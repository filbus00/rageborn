# Engineering log

The full project notes as they stood on 2026-10-01, moved here from `CLAUDE.md` when it was trimmed to the current state (the owner, 2026-10-02). It records how each system was built, what was measured and what went wrong, including the retired Wrathborn class. Search it by heading or class name when `CLAUDE.md` points here or a detail is missing there; where the two disagree, `CLAUDE.md` and the code are current.

## Project overview

Rageborn: isometric Diablo-style action RPG for iOS. Unity 6000.6.2f1, URP 2D renderer, new Input System only (`activeInputHandler: 1`, so never use `UnityEngine.Input`).

The design docs in `Docs/` are the source of truth for design decisions. Start at `Docs/00-vision-and-scope.md`. If code and docs disagree, ask before changing either.

- 2D isometric sprites: Isometric `Grid`/`Tilemap` for the world, sprite characters.
- Portrait only, iPhone only (no iPad in 1.0), iOS 16+, target 60 fps (`GameBootstrap`). No online features in 1.0 (no Game Center or leaderboards); iCloud save sync only.
- One-thumb control: a floating stick is the only input. Attacks and skills fire automatically, so there are no skill buttons, no tap-to-move and no dodge button.
- Company Filbus Software, bundle ID `com.filipbusic.rageborn`.
- Diablo 1 structure, not a survivor game: the player starts in a safe walkable town and descends a dungeon level by level by stairs. Enemies are packs placed in rooms that idle until aggro, and they never spawn around the player. See `Docs/00-vision-and-scope.md` and `Docs/05-world-and-content.md`.

## Layout

- `Assets/_Project/` holds all game content. `Assets/Settings/` (URP and input assets) comes from the Unity template.
- `Scripts/Runtime` is the `ARPG.Runtime` assembly (namespace `ARPG`), `Scripts/Editor` is `ARPG.Editor`.
- Physics/sorting layer names live in `GameLayers.cs`. `Tools > ARPG > Apply Project Setup` (`ProjectSetup.cs`) creates them in TagManager and applies iOS, identity and sorting settings. It is idempotent. Keep the two files in sync.
- `Scenes/Sandbox.unity` is the dev scene (built by `Tools > ARPG > Create Sandbox Scene`, which rebuilds the Grid if you run it again): isometric Grid (cell 1 x 0.5) with a `Ground` Tilemap of generated placeholder tiles and a portrait-framed camera (orthographic size 7.5: zoomed out from 8 to 10 at the user's request, then 25 percent closer on 2026-09-28, "The player really small and far away now"; Town and Dungeon have the same). Replace the tiles with real art later.

## Isometric conventions

- Tile art is 128x64 px diamonds at 128 pixels per unit (1 x 0.5 world units per cell).
- Transparency sort mode is Custom Axis (0,1,0): lower Y draws in front. Sprite pivots must be at the feet.
- Characters and props use the `Entities` sorting layer so they Y-sort against each other.
- Gameplay ranges are in ground space (1 unit = one tile width). Stick input is unprojected from screen space (screen Y doubled) before moving characters. See `Docs/01-core-gameplay.md`.
- No NavMesh in 2D. Enemy navigation is a grid pathfinder over the tilemap.
- In ground space the tile lattice is a square grid rotated 45 degrees: an edge neighbour is 0.707 away, a corner neighbour 1.0. `IsoMath.CellToGround`/`GroundToCell` convert (they assume the Grid sits at the world origin).

## Player, input and camera

- `StickMath` (pure) and `FloatingStickInput` (Enhanced Touch, mouse-simulated in the editor) produce a screen-space stick value. `PlayerController` converts it to ground space with `IsoMath` and drives a `Rigidbody2D`. `FollowCamera` follows with the lead and framing from the docs. `StickVisual` draws the stick on an overlay canvas.
- Pixel art (the owner, 2026-09-30: "I am not liking the art style. I want it pixelated", and of three readings, bigger pixels, a pixel-art look, or both, "Both"): `RenderResolution` adds URP's `PixelPerfectCamera` to each scene's main camera on load, in `UpscaleRenderTexture` mode, with a reference resolution of the screen over `Factor(long side)` (the whole number bringing the long side closest to `TargetLongSide`, 600: 3 on the owner's 2x iPhone 11, 276 x 597; 4 on 3x phones, 301 x 655 on an iPhone 17; it was 870, Diablo 2's size, from 2026-09-28) and a fixed `PixelArt.PixelsPerUnit` of 40, so one art pixel is one rendered pixel; the view's height follows the screen (14.9 units on an iPhone 11, 16.4 on an iPhone 17). `PixelArt` (pure) holds the palette (about 45 colours in dark-fantasy ramps), `Snap` and `Process` (hard alpha at half, palette, optional one-pixel outline in the warm near-black). The bake runs every frame through it (`SpriteBakeJob.pixelArt`, set by `WrathbornBakeSetup` and `EnemyBakeSetup`, both now at 40 a unit: the Wrathborn in 80 px cells, pivot (40, 12), about 53 px tall; enemies in 80 px cells, the ghoul 120), and `DungeonArt` draws at 128 a unit and averages down to 40 before `Process` (floors 40 x 20, walls 40 x 40 and 40 x 25 for the cut-low ones, props 40 x 40 outlined). The town's ground is repainted in those floors on load (`DungeonArt.PaveTown`, earth with flagstone where a slow noise says). Other world sprites (stairs, chests, NPC capsules, telegraphs, slashes, loot beams, shadows) are still smooth placeholders at 128 a unit, shown point-sampled at 40. The pipeline's render scale was tried first in 2026-09-28 and is left at 1: the 2D renderer enlarges a scaled render with bilinear filtering unless a Pixel Perfect Camera is present, so it came out soft. Screen space overlay canvases (HUD, bag, stick, damage numbers, Rage arc) draw after the upscale and stay sharp; world-space `TextMesh` labels are pixelated with the world. Game-view captures rendered by hand to a RenderTexture (the Notes' method) do not go through the upscale, so check the look on the simulator.
- Importing dungeon art (2026-10-01): PNGs named as `ArtNames` says (`floor_<flagstone|brick|earth|moss>_<n>`, `decal_<kind>_<n>`, `wall`, `wall_low`, `prop_<kind>`) go in `ArtSource/pixel/dungeon/` (outside Assets; README there); `Tools > ARPG > Import Pixel Art` (`PixelArtImporter`) shrinks each to 40 px wide (`PixelArt.Downscale`, exact blocks for 2x or 4x art), cuts floors to the diamond (`PixelArt.CutDiamond`), runs `PixelArt.Process` (props outlined), writes point-filtered, readable sprites at 40 a unit with the pivot 10 px up into `Resources/Art/Dungeon`, deletes outputs whose source is gone and reports to `Logs/PixelArtImport.txt` (sizes, palette distance). `DungeonArt` loads that folder once a play and uses an imported piece in place of its code-drawn one: a style's imported floor variants replace all its code variants (`DungeonArt.VariantCount`), a decal is an imported one stamped on the floor or else the code's drawn on it at 128 a unit, walls and props as they are. Written without Unity, not yet compiled or run.
- `FloatingStickInput` ignores a touch that begins over a UI element, so a tap on an inventory-screen button inside the stick's touch zone starts that button, not the stick underneath it. It raycasts the UI at the touch itself (`IsOverUi`, `EventSystem.RaycastAll`): `IsPointerOverGameObject` asks the UI input module, which has not seen a touch on the frame it begins, and on the simulator on 2026-09-28 a tap on the Bag button moved the character instead.
- `Tools > ARPG > Add Player And Camera To Sandbox` generates the placeholder art, the `Player` prefab and the scene wiring. It rebuilds the Player, Stick Input and Stick Canvas objects if run again.
- `FollowCamera`'s lead is capped at `leadDistance`: it scaled with speed over move speed, so Bull Rush (16 per second) pushed the view about 6 units ahead and back, and the camera seemed to lose the character (the owner, 2026-09-29).
- Components find each other at runtime (`FindAnyObjectByType`) when their reference fields are empty.
- EditMode tests are in `Assets/_Project/Tests/EditMode`. The pure math (`StickMath`, `IsoMath`) has no Unity scene dependency.

## Enemies

- Enemies are placed as packs, never spawned around the player (see the structure note above). `EnemyPack` (3 to 12 members) spawns its members from the pool around its position when the level loads. Members idle at their home spot until the player is within aggro range, chase, and after the leash breaks (beyond 20 units for 4 s) walk home and idle again (`EnemyState.Return`). Killed enemies stay dead: a pack never respawns a member and counts `KilledCount`. Kills are saved to disk with the character (see Saving).
- `EnemyManager` owns the pool and everything enemies share: a `NavGrid` baked by `NavGridBaker` (a cell is walkable when the Ground tilemap has a tile and no tilemap on the Obstacle layer does), a `FlowField` (one Dijkstra from the player's cell, not A* per enemy) and a `SpatialHash` of enemy positions. It ticks every `EnemyController` once per frame, so enemies have no `Update`. Each pack builds a lazy flow field to its own center so returning enemies route around walls.
- Enemies have no Rigidbody or collider. They live in ground space and only the transform is projected with `IsoMath`. Find neighbours and targets through the spatial hash. A wall is one cell thick (0.707), so `EnemyController.Move` splits long steps into pieces of 0.25 or less; without that, a frame hitch let an enemy jump a wall. Keep the per-frame path allocation free: over 6000 update triples of an unbroken fight (manager, combat and loot) the heap did not grow, and the manager's `Update` took 0.02 to 0.07 ms with 40 enemies, both in the editor and not on a phone. See the note on measuring allocations under Notes.
- `EnemyDefinition` (ScriptableObject) holds the tuning. Its values marked as tuning are not in the docs yet. States are Idle, Approach, Attack (a 0.35 s wind-up during which the enemy swells as a tell, then the hit lands if the player is still within reach plus 0.3), Recover (0.65 s), Return and Dead (a short fade, then back to the pool). The swarmer's attack numbers are tuning values, since the docs give none; a level 1 hit is 3 damage from the docs' curve. `TakeDamage(float)` takes damage that has already been through the hit formula, and a hit wakes an idle or returning enemy.
- Rank (`EnemyRank`: Normal, Champion, Elite, Boss; Docs/00 and Docs/03-itemization.md): a pack has at most one Champion (its lone leader, `EnemyPack.championDefinition` applies to slot 0 only) or is entirely Elite (just give the whole pack an Elite `definition`). Rank drives, all read from `EnemyDefinition.Rank` at the point of use, not cached: which `LootSource` a kill rolls against (`LootDirector`), the 30 percent target-priority weight for Elites in `PlayerCombat.PickTarget` → `SweepGeometry.PickTarget`'s optional weight list, and the 15 percent player-armor-ignore on an Elite's (or the boss's) own attack (`EnemyController.LandAttack` → `PlayerHealth.TakeHit`'s `armorIgnorePercent`). A Champion or Elite gets its own placeholder body sprite (`EnemyDefinition.BodySprite`, swapped onto the pooled `EnemyController`'s "Body" renderer in `Activate`, reset to the prefab's default when absent) rather than a runtime color tint: `SpriteRenderer.color` multiplies the sprite's own already-red pixels, so tinting can only darken toward brown, never reach a clean gold or crimson — caught by actually looking at a capture, not just trusting the code. `VisualScale` (a plain size multiplier, unaffected by that problem) still works as a runtime multiply.
- Elite modifiers (`EliteModifiers`, a `[Flags]` enum; Docs/01-core-gameplay.md): a curated slice of the docs' eight — Hasted (plus 30 percent move and attack speed), Vampiric (heals on a landed hit) and Frozen (slows the player on a landed hit) — the three that hook into stats and systems already built, without needing a new hazard-area (Molten), shield/absorb (Shielded), steering-override (Teleporting), add-spawning (Splitting) or resistance (Cursing) system. `EliteModifierRoller` (pure, tested) rolls one or two, never repeated, only for `EnemyRank.Elite`; `EnemyManager.Spawn` rolls them (its own unseeded `System.Random`, flavor randomness like the crit roll, not economy like loot) and passes them into `EnemyController.Activate`. `EnemyController.EffectiveMoveSpeed`/`EffectiveAttackWindupSeconds`/`EffectiveAttackRecoverSeconds` apply Hasted; `LandAttack` applies Vampiric (heal, capped at max life) and Frozen (`PlayerController.ApplySlow`, via the new `EnemyManager.PlayerController` accessor). The player's `SlowDebuff` (pure, tested) is a simple multiplier-below-1 with a timer: reapplying while active keeps the stronger slow and the longer remaining duration rather than stacking multiplicatively, so repeated Frozen hits cannot creep speed toward zero. Each active modifier shows as a small colored dot above the elite's head (`EnemyController.UpdateModifierIcons`, up to `MaxModifierIcons` = 2): Hasted yellow, Vampiric green, Frozen cyan. The icons are their own white placeholder sprite (`PlaceholderArt.Disc`) tinted per modifier, not a tint on the body sprite, and live on the `WorldUI` sorting layer so they always draw on top; they are excluded from the `renderers` array `SetVisuals` resets to white every windup/punch/death tick, or that would stomp their color right back off. Vampiric started as red before this was checked against a capture: every enemy sprite in this project is already red or crimson, so a red dot barely read against its own owner: it is green now, chosen to stand apart from the rest of the palette, not for any lore reason. Shielded/Teleporting/Splitting/Molten/Cursing are not built.
- Archetypes (`EnemyArchetype` on `EnemyDefinition`; Docs/01-core-gameplay.md, enemy behavior): Swarmer (the husk: bites at reach), Brute and Archer. Act 1's two new enemies are the ones Docs/05 names: the **Ghoul** (Brute, `Data/Enemies/Ghoul.asset`: 3 times a husk's life, 2.2 times its hit, speed 2.2; starts a slam within 1.6, which paints a 2 unit ground circle filling over 0.9 s where it stood and hits only if the player is still inside, however close the ghoul is) and the **Bandit Archer** (Archer, `BanditArcher.asset`: 0.7 times the life, 1.2 times the hit; shoots only with line of sight and within 7.5: a thin aim line for 0.4 s, the docs' projectile telegraph, then an arrow at 9 units per second that walls stop; between shots it closes in when it cannot see the player, backs off below 4.25 (`ArcherSteering`, preferred 5 minus a 0.75 band) and otherwise holds). Numbers other than the slam radius and the 0.4 s line are tuning. Telegraphs reuse the boss's `GroundMarker`, one slam and one aim marker per pooled enemy made on first use and reused (`RestartCircle`/`RestartLine`/`Hide`), parented to the Enemy Manager; arrows are `EnemyProjectiles`, a sprite pool the manager ticks after the enemies, flown by the pure `EnemyProjectileFlight` (pieces of 0.25 so a hitch cannot pass a wall, a 0.4 hit radius, spent past range plus 2). Damage and the elite armor ignore are fixed when the arrow is fired; Vampiric and Frozen apply on the arrow's hit if the shooter still lives. Neither type gives more XP or loot than a husk yet (the docs scale rewards by level and rank only). `Tools > ARPG > Create Act 1 Enemies` creates the two definitions if missing; Create Dungeon Scene does it too and wires them into `DungeonLevel`.
- Baked enemy art (2026-09-28): `EnemyDefinition.SpriteCharacter` names a baked character in Resources/Characters (`husk`, `ghoul`, `bandit_archer`; a rank may name its own look, `husk_champion`, or share the base). `EnemyAnimationSet.For` loads its idle, run, attack, hit and death sheets once per type (a shared static cache, misses included) and the pooled `EnemyController` animates its "Body" renderer from them in `Animate`, which the manager calls after `Tick`: the attack runs through the wind-up to the strike at `EnemyAnimationRules.HitFraction` (0.55, tuning) exactly when the game lands the blow, then through the recovery; a 0.25 s hit reaction when struck outside an attack; the run at the enemy's speed over the run's recorded speed; else the idle; facing the player while attacking (an archer its aim), else the way it moves, with the player's row margin; death over `DeathSeconds` under the dissolve. With sheets, the body sits at its feet at scale 1 and the placeholder swell and shrink tells are off (the art's own wind-up and fall are the tells); `VisualScale` still sizes ranks. Without sheets nothing changes. The sheet loading is `CharacterSheets` (shared with `LayeredCharacterSprite`). The bake: `Tools > ARPG > Sprite Bake > Bake Enemies` (`EnemyBakeSetup`) takes each folder `Art/Models/Enemies/<name>/` (`<name>.fbx` with skin, `<name>_run/_attack/_hit/_death.fbx`, `<name>_albedo.png`; README there), sets up the rig and in-place clips with `MixamoImport` (the helpers moved out of `WrathbornBakeSetup`), cuts one-shots to their action, bakes 8 directions at 64 px a unit (128 cells, pivot (64, 20), the brief's heights: husk 70, ghoul 88, archer 80, asked 9 percent over for the A-pose box), and wires the definitions (`Wire Enemy Looks`). ## Survival, town and session

- `PlayerHealth` (on the `Player Vitals` object, with `DeathFlow`) holds a `LifePool`, applies armor and raises `Died`. Both `Armor` and `MaxLife` read live from `GameSession.Current.Equipment` (see Loot); `PlayerHealth` rescales the `LifePool`'s max, keeping the current fraction, whenever `GameSession.Changed` fires, so equipping more life updates without a scene reload. Life is carried between scenes in `GameSession`, so stairs do not heal. Life comes back from the auto-potion (see Auto-potion), a level up, and the Life on Hit affix; there is no regeneration yet.
- `GameSession` (pure, tested) is everything that must survive a scene change within one game session: equipped gear, the backpack, gold, corpses, which pack members were killed, life and the loot roller (so its bad-luck counter survives). `GameSession.Current` is replaced at the start of every play (`RuntimeInitializeOnLoadMethod`), because the project runs with domain reload off and statics would otherwise leak between editor plays. A future sleep mechanic resets it. It is saved to disk (see Saving) and a loaded save replaces it at startup (`GameSession.Install`).
- Death (`DeathFlow`): the character stops, its equipped gear becomes a `Corpse` at the death spot, and the screen fades to the `Town` scene. Only equipped gear is left; a death with nothing equipped makes no corpse and leaves the first one where it is. Corpses never expire. `CorpseSpawner` places a `CorpseMarker` for each corpse of the current scene, and walking onto it picks the gear back up. A character with no weapon fights unarmed, valued by the weapon curve at item level 0 (damage 6). Weapon, Chest and Helm exist as gear (see Loot).
- Killed enemies stay dead: `EnemyPack` records each kill by level id (`LevelContext.CurrentId`: the scene name for a hand-built scene, "Dungeon 3" for a generated level), pack object name and slot in `GameSession`, and skips those slots when the level loads again. Pack object names must therefore be unique within a level. Corpses and opened chests use the same level id.
- Stairways are `SceneExit` triggers (walk onto them, no button) that fade and load a scene by name; they wait 0.75 s after they are created (measured with `Time.time`: during a scene's first `Awake` calls `timeSinceLevelLoad` still holds the previous scene's time, which once left the next level's stairs dead for as long as the last level had taken) so arriving next to one does not bounce the player. The player arrives wherever the target scene placed it, except in the dungeon scene: a stairway into it also carries a depth and which stairs to arrive by (`SceneExit.Configure`, `GameSession.Travel`). The build contains Town then Dungeon (`DungeonSceneBuilder.WriteBuildSettings`); the Sandbox is a development scene only. Scene names are referenced as strings in `DeathFlow`, the stairways and `DungeonLevel`.
- The HUD is a life bar (`LifeBar`) and a black fade overlay (`ScreenFade`) on two overlay canvases. Its layout (the owner, 2026-09-28) is applied at runtime by `HudLayout.Arrange` (called from `InventoryScreen.Awake`), so the scenes are unchanged: inside the safe area, a round portrait top left (`CharacterPortrait`: the baked idle's first south frame, body, helm and weapon stacked, masked to a circle, following the gear on `GameSession.Changed`) with the level on a badge at its foot, the life bar, experience bar and potion pips to its right, and the Bag button under it (no longer mirrored by handedness, which now moves only the Portal button); the dungeon's mini-map top right with no backdrop (`Minimap`). The development perf overlay is two faint lines (50 percent) with no backdrop under the Bag button, inside the safe area (2026-09-29: in the band beside the Dynamic Island the rounded corner cut it, and on the owner's iPhone 11 the notch leaves no room for it; an `iPhone 11 (Rageborn)` simulator, D38E7E50-961A-422C-9B72-E6DF43CC36B9, shows his phone's layout).
- `Tools > ARPG > Add Survival To Sandbox` builds the HUD, the vitals object, the corpse spawner and the stairway up. `Tools > ARPG > Create Town Scene` copies the sandbox to `Scenes/Town.unity` and strips it of enemies, combat and walls, leaving the ground, the player, the HUD and a stairway down, and writes the build settings. Rebuilding the sandbox means rerunning the later steps (full order under Dungeon).
- The town has the Forge smith (see Forge) and the Waystone (see Travel). The Stash and Trainer NPCs are not built.

## Loot

- Items are pure data (`Item`: slot, rarity, item level, affixes). All ten slots are built: Weapon, Chest, Helm, Gloves, Boots, Belt, Amulet, two rings (2026-09-28) and the off-hand (2026-09-29). Item kinds add `Shield` and `TwoHandWeapon`; `ItemSlot.OffHand` and `Ring2` are only places to wear things. The grips (`GripRules`, Docs/03 Q10, numbers tuning): a shield in the off-hand blocks 12 percent of melee hits and projectiles plus 4 per look tier (`PlayerHealth`, rolled apart from dodge, capped at 50, a BLOCK callout); a second one-handed axe in the off-hand is dual wield, basic swings alternating hands with each weapon's own damage (`PlayerCombat.offHandSwing`; skills use the main hand), 15 percent more attack speed, both weapons' affixes counting; a two-hander (the great axe) hits 1.6 times as hard at 0.85 times the speed and reaches 0.3 further (`PlayerCombat.BasicRange`). `EquipmentState.Equip` applies the rules: a two-hander empties the off-hand, an off-hand item takes a two-hander out, and `GameSession.EquipFromInventory` refuses when the backpack cannot take everything that comes off. `PowerScore.PlaceFor` puts a one-handed axe in the main hand when it is empty or holds a two-hander, otherwise where it scores higher (replacing the main axe or joining it); the score counts block, the grip's attack speed and dual wield's average swing. Shields roll Life and Armor (no built suffix); two-handers roll what weapons roll. `ItemSlot.Ring2` is only a place to wear a second ring, never an item's kind: `EquipmentState.PlacesFor(kind)` gives a ring both hands, and `PowerScore.PlaceFor` puts a ring on an empty hand, else in place of whichever ring it beats by more. Worn items are saved by kind and a second ring is put on the second hand when loaded, so the save format did not change. A weapon's damage and an armor piece's protection come from item level alone (`WeaponAverageDamage`, `ArmorValue`: chest and helm the full armor curve, gloves and boots 60 percent, a belt 40, jewellery none, Docs/03's proposed table); affixes add on top.
- `Affix`/`AffixTable`/`AffixRoller` (pure, tested): a curated slice of the 88 affixes in `Docs/03-itemization.md` — 4 prefixes (flat weapon damage, increased damage, life, armor) and 7 suffixes (attack speed, critical chance, critical damage, life on hit, cooldown reduction, movement speed on boots, dodge chance on boots, belts and rings; the last two added 2026-09-28 so boots and belts have suffixes), each rolling on the slots Docs/03 lists for it, with 5 tiers gated by item level (T5 unlocks at level 1, T1 at level 60) and a value rolled uniformly within the tier's scaled range. Affix counts by rarity follow the docs (Common 0, Magic 1 and 1, Rare and Legendary 2 to 3 of each), capped by how many of that kind a slot has eligible: a belt, for example, has only Life and Dodge so far, and a ring only Flat damage among the prefixes. Legendary reuses Rare's affix range; fixed legendary affixes and unique powers are not built.
- `LootRoller` (pure, seeded, tested) follows `Docs/03-itemization.md`: a normal enemy drops an item 6 percent of the time, rarity weights 60, 30, 8.5 and 1.5, Magic Find multiplies the top three, and the legendary weight doubles after 300 kills without one and triples after 600 (every kill counts). A drop's slot is chosen uniformly among the eight kinds (a weapon is now 1 drop in 8, not 1 in 3); there is no per-slot drop table yet. Gold is `0.6 * level^1.3` rounded, with a floor of 1. Item level equals the enemy's level. The live session seeds its roller from the clock; pass a seed to replay.
- `LootSource` also has `Champion` (25 percent drop, 1 item, Magic floor) and `Elite` (100 percent, 1 to 2 items, Magic floor or 30 percent of the time Rare — one roll per kill, not per item, so a 2-item elite drop either both floor at Rare or neither do) and elite gold is 8 times the normal formula, Champion gold 3 times (the user asked for more than normal; 3 is a tuning value). `RollDrops` is the plural, canonical roller; `RollDrop` (singular) wraps it and returns the first item, unchanged behavior for `NormalEnemy`. `LootDirector.OnKilled` picks the source from the dying enemy's `EnemyDefinition.Rank`.
- `EquipmentState` (in `GameSession.cs`) holds one item per slot, immutable (`With` returns a changed copy). It sums each affix-derived stat across every equipped item (`TotalArmor`, `TotalLifeBonus`, `FlatWeaponDamageBonus`, `IncreasedDamagePercent`, `AttackSpeedPercent`, `CriticalChancePercent`, `CriticalDamagePercent`, `LifeOnHit`, `CooldownReductionPercent`), so a future slot or affix granting the same stat just adds in. `PlayerHealth` and `PlayerCombat` (damage, attack speed, the crit roll, life on hit healing, cooldown reduction) read these live every use, not cached.
- `GameSession.PickUp` only bags a found item now; nothing is auto-equipped. Equipping is the player's choice from the inventory screen (`EquipFromInventory`, `Unequip`, `Discard`, all pure and tested). `Retrieve` (walking onto your own corpse) still restores gear automatically, slot by slot as one all-or-nothing transaction, equipping a piece when the slot is empty or it raises the power score.
- `LootDirector` (on a `Loot System` object) listens to `EnemyManager.Killed`, rolls gold and an item and places them from a pool of drop objects. `DropItem` and `DropGold` are public for chests. Drops still on the ground are lost when the scene changes.
- `LootDrop` draws a floor marker and, for items, a beam whose color and height follow rarity (colors from `Docs/06-ui-ux.md`, heights are tuning values).
- Auto-loot (`PlayerLoot`, rules in the pure `AutoLootRules`): everything within 2.5 units; gold always, items only when the character has not been hit for 1.5 s or nothing is engaged with it. An item stays on the ground if the 40 slot `Inventory` is full.

## Dungeon

- Levels are generated (`Docs/05-world-and-content.md`, level generation) as connected halls in the manner of Diablo 1's cathedral (the owner, 2026-09-30, replacing rooms joined by corridors). `DungeonGenerator` (pure, tested over 40 seeds x 6 depths) grows a tree of room slots from the start room on a grid whose columns and rows each get their own width (`DungeonSettings.MinRoomSpan`/`MaxRoomSpan`, 18 to 32 cells; the boss arena's column and row are exactly its 36), so rooms sit wall to wall sharing one wall line; the exit room is the one deepest in the tree. `Join` opens a tree edge as an arch 5 to 11 wide at a random place along the shared wall or, 30 percent (`HallJoinChance`), the whole wall bar a 2 cell pier at each end; other neighbours get an arch 45 percent of the time (`LoopChance`), never into the arena (its one way in is 5 wide at the middle of its side). `Dress` stands pillar rows, a pillar grid, wall stubs or a hand-authored template's pillars (centred, when it fits) in combat, elite and treasure rooms; openings clear 2 cells in front of them afterwards, and `KeepReachable` walls off any floor the dressing cut off. Each level: a start room (no packs) with the stairs up, 5 to 8 middle rooms, an exit room with the stairs down; combat 75, elite 15, treasure 10 (the docs' shrine 10 and ambush 5 go to combat until those rooms exist); at least one elite room and pack and one treasure room with a chest. Combat rooms hold 1 to 2 packs when small, 2 to 3 medium, 3 to 4 large (by the side of a square of the same area); packs are 6 to 12 swarmers (25 percent with a Champion leader), elite packs 3 to 4 (a large elite room adds a normal pack), a treasure room's guard 3 to 5; they need 75 percent of their disc on floor and are kept out of aggro range (plus their radius and 1.5) of both arrival points, which the tests check. The stairs sit in their room's corner furthest from its openings, with the arrival point toward the room's middle. A generated depth 3: 9 rooms, 6,234 floor cells, 143 enemies, 134 props, 199 decals, 7 ms.
- Dressing (2026-09-30, the owner's "different floor textures, brushes, and whatever fits inside a dungeon"): each room has a floor style (`RoomPlacement.Style`: flagstone, dark brick, packed earth, mossy stone). `DungeonDressing` (pure, tested) places props (`DungeonCell.Prop`, `DungeonLayout.Props`: barrel, crate, urn, bone pile, rubble, broken column, sarcophagus, brazier, candles; one per 70 floor cells, barrels and crates in twos and threes) against walls, 4 cells clear of openings, 2 of the stairs, arrivals, waypoint, chests and Wanderer, outside pack discs, and only where `SafeToBlock` finds the cell's walkable neighbours on one unbroken run around it, so the floor stays in one piece; at most one lit prop a room. Decals (`DungeonLayout.Decals`: cracks, bones, blood, rubble, moss (mostly in mossy rooms), a skull, puddles; one per 30 floor cells) are walked over. `DungeonArt` draws all of it in code at first use (floor tiles 128 x 64 in 3 variants per style, the decal drawn into a copy of the tile; props 128 x 128 in the wall tile's frame, pivot at a quarter height, `ColliderType.Grid`), cached for the session. `DungeonLevel.Paint` puts props on the walls tilemap (Obstacle layer, so the nav grid and the player's collider treat them as walls), tints walls by their room's style with a per-block shade, lights braziers and candles with a flickering `Light2D` (`FlickerLight`), and cuts only outer and dividing walls low on the camera side: a pillar inside a room keeps its height (cut low, a 2 x 2 pillar read as a cross of stubs). The scene's old checkerboard `floorTiles` are no longer painted.
- Rooms are hand-authored as text (`RoomShape`, `RoomTemplate` assets in `Data/Rooms`): '.' floor, '#' pillar, square, the middle 5 cells of each side and 2 rows inside kept clear for doorways, every floor cell reachable; `RoomShape.Parse` rejects anything else. Sizes up to 22 are small, up to 30 medium, up to 36 large (about 25 ground units). Six placeholder rooms (`PlaceholderRooms`, two per size: 20, 28, 36), mostly open halls with a few pillars, after the user found the first set (14 to 26 cells, more pillars, 3 cell doorways) too small and cramped; the docs want 30 per act. Create Dungeon Scene only adds missing templates, so edits survive.
- `DungeonRules`: 6 levels per act; enemy levels by depth 1, 2, 3, 4, 5, 7 (tuning, chosen with the balance report so they follow the level a full clear reaches; the first version spread Docs/05's 1 to 12 evenly and the character fell three levels behind; the user's decision of 2026-09-26, act 1 now ends near character level 7). Changing them changes no layout, so no generator version bump. A level's seed mixes `GameSession.DungeonSeed` (saved) with the depth, so every level keeps its layout for the session and only one number is saved. The last level has no stairs down: its exit room is the boss arena (see Act boss).
- `DungeonLevel` (in `Scenes/Dungeon.unity`, `DefaultExecutionOrder(-200)`) builds the level in Awake, before `EnemyManager` bakes its nav grid from the painted tilemaps and before the packs spawn: paints ground and walls, places the player by the right stairs (`GameSession.Travel`, set by the stairway that led here; opened directly in the editor it builds `editorDepth` from above), and creates the stairs (`SceneExit.Configure`), chests and packs (`EnemyPack.Configure`, with the depth's enemy level). A level spawns all its packs at once: over 50 generated levels, 51 to 160 enemies (112 on average) in about 7,000 floor cells, generated in about 6.5 ms in the editor; the pool is 200.
- Per-enemy level: `EnemyController.Level` (set at spawn, else the definition's) drives life (`EnemyDefinition.MaxLifeAt`), hit damage, armor, loot item level and XP, so one definition serves every depth.
- Chests (`Chest`): walk onto one to open it; `LootDirector.DropChest` rolls `LootSource.ZoneChest` (docs: always drops, 1 to 3 items, Magic floor; gold 5 times a normal enemy's, tuning; opening one does not count as a kill for bad luck protection). Opened chests are remembered per level in `GameSession` and saved (format 4).
- `Tools > ARPG > Create Dungeon Scene` copies the sandbox to `Scenes/Dungeon.unity`, strips the test room, its stairway and all tiles, sets a black background, a pool of 200, adds `DungeonLevel` with its references, creates missing room templates and the chest art, and writes the build settings (Town, Dungeon). The town's stairs lead to dungeon depth 1. Full build order: Create Sandbox Scene, Add Player And Camera, Add Enemies, Add Test Room, Add Combat, Add Survival, Add Loot, Add Inventory Screen, Create Town Scene, Create Dungeon Scene. Build the chest art before loading room templates: an asset import in between left the scene's references to freshly created templates null the first time.
- `DungeonGenerator.Version` (4; 3 added the boss arena, 4 connected halls and dressing) is saved with the dungeon seed (save format 5). Bump it whenever the same seed would build a different level: a save from another version forgets its dungeon kills and opened chests (`GameSession.ForgetDungeonLevels`, which leaves hand-built scenes alone), since they are keyed by pack and chest number and would land on different ones. Found when the bigger rooms loaded a save whose old kills left most packs of the new layout missing. Corpses are never dropped: `DungeonLevel` moves one whose spot is no longer floor to the arrival point (`GameSession.MoveCorpse`).
- Mini-map (`Minimap`, added to each level by `DungeonLevel`, builds its own canvas at sort order 15; `Docs/05` and `Docs/06`): `MinimapReveal` (pure, tested) reveals every floor and wall cell within 10 of the player and, on entering a room, the whole room and its walls. The map is a one-pixel-per-cell texture, turned 45 degrees under a half-height parent so it lies like the isometric view (up on the map is up on screen), redrawn at most every 0.2 s and only when something new was seen. The small map (top right, under the potion pips) shows a 48-cell window around the player with the stairs and chests once seen (opened chests dimmed) and a green arrow on its rim toward the stairs down while they are out of view; 80 cells made rooms specks on the phone, and a pure black backdrop vanished into the black void. A tap on it toggles the whole level, large and see-through, above the player; the game keeps running and the large view takes no touches, so the stick works under it. Explored cells are kept per level in `GameSession.ExploredCells` for the session but not saved, so a loaded game starts with blank maps. The development perf overlay moved to the top left to make room.
- Pack mixes (`PackComposition`, pure, tested; tuning, the docs name act 1's enemies but not how they mix): depth 1 is husks only; deeper, a normal or champion pack is husks only (40 percent), husks with 2 or 3 ghouls (25), husks with 2 or 3 archers (20), or a band of 3 ghouls and 2 archers and nobody else (15). Ghouls and archers take a pack's last slots, which the sunflower spiral puts on the outside; a Champion keeps slot 0; elite packs stay husks. It is hashed from the level seed and the pack number, outside the generator's random stream, so adding the types left every layout and saved kill in place (no generator version bump); `EnemyPack.Configure(EnemyDefinition[] perSlot, ...)` spawns one definition per slot and skips null ones. A generated depth 3 held 67 husks, 10 ghouls and 11 archers besides champions and elites.
- Low walls on the camera side (the user's decision of 2026-09-27, Docs/09 section 14.3, as in Diablo 2): `WallRules.IsCameraSide` (pure, tested) marks a wall cell with floor behind it on screen (at x + 1, y + 1 or both, since a cell sits higher the larger its x + y), and `DungeonLevel.Paint` draws those with `lowWallTile` (the placeholder block cut to a 16 px stub, `Art/Tilesets/PlaceholderWallLow.asset`), the far walls full height. Colliders and the nav grid are per cell, so a low wall blocks exactly as a tall one. `Tools > ARPG > Add Low Walls To Dungeon` adds the tile to the existing scene; Create Dungeon Scene sets it too. The first run lost the tile: it was created before `OpenScene`, which unloaded it; it is now loaded again by path after. Checked in play mode on 2026-09-27: the character stands behind a camera-side wall in full view. Pillars come out low in front and tall behind.
- Not built: shrine and ambush rooms, acts after the first, the wolves Docs/05 lists for act 1 (no archetype given), and the Caster, Charger and Support archetypes.

## Forge

- Follows the Forge in `Docs/03-itemization.md` with the user's decisions of 2026-09-26 (logged in `Docs/08-production.md`): the first version has Salvage, Reforge affix, Reroll values and Temper; Socket, Imprint and Transmog wait for gems, legendary powers and appearances. Salvage and every Forge action happen only at the smith in town; the dungeon keeps Discard, which returns nothing. The loot filter's auto-salvage now conflicts with that (open question 9).
- `ForgeRules` (pure, tested) holds every rule and number. Salvage: Common 2 Ash, Magic 2 Cinders, Rare 2 Bloodstone, Legendary 1 Soulglass (`CraftingMaterial`). Reforge (Rare only): the chosen affix becomes a random affix of the same kind (prefix or suffix) the slot can roll and the item does not already carry elsewhere, at the same tier, with a fresh value; it may land on the same stat, and on a weapon a prefix always does, since weapons have only two prefixes. It costs 2 Bloodstone and 10 times the docs' gold curve (`0.6 * itemLevel^1.3`), both times 1.25 per earlier reforge of that item, rounded up (the docs escalate the material; the gold escalating too is their "gold that rises with each reroll"). Reroll values (Legendary only): every affix's value again within its tier, 1 Soulglass and 15 times the curve. Temper (any item with affixes): one affix a tier better, its value keeping its place in the range (top of T3 lands at the top of T2), at most 3 per item, 2 Soulglass and 25 times the curve. Elites also give 1 Bloodstone and the boss 3 Soulglass straight to the character (`LootDirector.GrantMaterials`, with a callout), since Docs/04 lists them as sources. All amounts and multipliers are tuning values.
- Each action returns a new `Item` (items stay immutable); `Item.Reforges`/`Tempers` carry the counts and are saved. `GameSession.ApplyForge` pays and swaps the result into the same backpack position (`Inventory.Replace`) or the worn slot, or changes nothing when the original is gone or the cost cannot be paid. `GameSession.ForgeRandom` is seeded from the session like the loot roller. Materials live in `GameSession` (`Materials`, `AddMaterial`, `Salvage`) and are saved by name (save format 6).
- `ForgeNpc`: the smith in town (`TownSceneBuilder`, cell (-4, 4), a placeholder grey capsule labeled Forge; `Tools > ARPG > Add Forge To Town` adds or rebuilds just the smith, Create Town Scene includes it). Walking into its trigger opens `ForgeScreen`; to open it again, walk away and back.
- `ForgeScreen` (built in code on its own canvas at sort order 50, like the inventory screen): a bottom sheet with the wallet (gold and the four materials, each in its rarity's color), tabs Salvage, Reforge, Reroll, Temper, a one-line explanation, the item list and the detail. Salvage lists the backpack with each item's yield and a Salvage button, plus "Salvage all Common and Magic". A crafting tab lists the items it can work on, worn first; picking one shows its affixes as 48 point buttons (Temper shows the next tier's range), the cost with what is short in red, and the action button, disabled until an affix is picked and the cost can be paid. After an action the result stays selected with a "before → after" line, so a player can go again. It does not pause the game (the town has no enemies); the full-screen backdrop keeps touches off the stick.
- Checked on 2026-09-26: in play mode every action through the sheet's own buttons (two reforges with the cost rising 152 → 190 → 238 gold and 2 → 3 → 4 Bloodstone, the button disabled when short, a temper T5 → T4, a reroll, bulk salvage), and on the iPhone 17 simulator walking up to the smith, the Salvage and Reforge tabs. The simulator showed the first affix buttons at 37 points, under the docs' 48; they are 48 now, and a five-affix weapon was measured to still fit the sheet. ## Act boss

- The Cinder Warden, act 1's boss (`Docs/05-world-and-content.md`), waits in an arena that replaces the exit room of the act's last level (depth `DungeonRules.LevelsPerAct`): `DungeonGenerator` gives that room kind `RoomKind.Boss` and a 36-cell disc (`BossArenaShape`, radius 18 cells, about 12.7 ground units) and records `BossArenaCenter`/`BossArenaRadius` on the layout; no packs spawn in it, and the elite-room fallback skips it. Tests check the arena exists only on the last level, is floor at its center and is reachable.
- `EnemyRank.Boss` routes through the same places as the other ranks: `LootSource.Boss` (always 4 to 6 items at a Rare floor, and one roll per kill, 35 percent, turns the first into a Legendary; gold 20 times a normal enemy's), 60 times normal XP (`Experience.BossXpMultiplier`), the Elite targeting weight and the 15 percent armor ignore. All of these multipliers are tuning values. Its definition (`Data/Enemies/CinderWarden.asset`, made by Create Dungeon Scene if missing) has 30 times a normal enemy's life: about 9,700 at level 7, about 70 s for the balance report's character (level 6, typical gear), inside the docs' 60 to 120 s for a zone boss. It was 15 until act 1's enemy levels were flattened, which put the fight at 35 s; raised at the user's request (2026-09-26).
- `CinderWardenFight` (created by `DungeonLevel.SetUpBoss`) spawns the boss through `EnemyManager.Spawn` and sets `EnemyController.Scripted`, so the controller only animates, takes damage and dies while the fight moves it (`ScriptedMove`) and picks its attacks. It engages when the player enters the arena or hits the boss (`EnemyController.Damaged`), and resets (not heals) if the player leaves the arena by 3 units or dies. Attacks are `IEnumerator`s stepped once per frame from `Update` (not coroutines, so a stagger or phase change can drop one cleanly), each telegraphed on the ground by a `GroundMarker` (runtime sprites from `TelegraphArt`, on the Decals layer) that fills before it lands. Phases by life (`BossPhases`: below 2/3 and 1/3; a phase change flashes the screen and cancels the current attack): 1 slam (radius 3.2, 1.1 s fill) and a 5-ember volley; 2 adds the fire ring (a 3.5-unit band at the arena edge that fades in over 1.5 s, then burns 0.7 hit per second) and burning husks (4 swarmers every 12 s, up to 10, already aggroed); 3 three-charge chains (0.5 s line each) and rain (5 circles around the player, one hit at most). Entering phase 3 directly also lights the fire ring. Damage is the enemy hit curve at the boss's level times an attack multiplier (slam 1.6, embers 0.6, charge 1.3, rain 0.9), all tuning values.
- Stagger (`StaggerMeter`, pure, tested): every hit adds 3.5 of 100; full, the boss stands still and does nothing for 3 s, its current attack cancelled, then the meter starts empty. Hits during a stagger do not count.
- `BossBar` (its own canvas, sort order 16): the name, the life bar with phase marks at 2/3 and 1/3, the stagger bar with a STAGGERED label, and the full-screen phase flash.
- The kill is recorded as `<level id>/Boss` slot 0 and saved at once. The fight then adds Stairs To Town near the arena's far edge, not in its middle (there is no act 2 to go down to), and a reload of the level with the boss dead places them straight away. `SceneExit` arms 0.75 s after its own `Awake`, so stairs created mid-level also wait.
- `DevShortcuts` (development builds and the editor only): the town gets orange stairways labeled "DEV: depth 3" (the first depth with every enemy type, cell (12, 0); it was (9, 1) until 2026-10-03, where its label ran into the Pet Vendor's) and "DEV: boss" at cell (9, 5) that lands the player inside the boss arena (`Arrival.AtBoss`, three cells inside the rim, `DungeonLayout.BossArenaEntry`, which the tests check is floor). The first version arrived at the level's start, a level's worth of packs away from the arena, which was no shortcut.
- Checked in play mode on 2026-09-26 with a test character (life boosted, then unarmed so the fight lasted): every attack of every phase with captures, the fire ring and husks, the stagger (label shown exactly 3 s, the boss still, attacks resumed), and a kill that recorded the boss, placed the stairs, dropped 3 Rares and a Legendary at item level 12 and took the level 1 character to level 6. Found and fixed there: a burst from phase 1 straight into phase 3 skipped the fire ring. On the iPhone 17 simulator the same day: the DEV stairs, the boss bar with its phase marks, the slam telegraph and the stagger bar filling, at 60 fps with 146 enemies on the level.
- Not built: bosses for later acts, boss sounds and art, the docs' reduce-flashing setting for the phase flash.

## Auto-potion

- `AutoPotion` (pure, tested) follows `Docs/01-core-gameplay.md`: it fires by itself at 35 percent life (the docs make that configurable from 20 to 60 in Settings, which do not exist yet; `TriggerFraction` is clamped to that range) and heals 40 percent of max life spread evenly over 3 s. Tuning values the docs leave open, picked here: 3 charges at most, 10 kills refill one (kills while full are not banked), no second potion while one is healing, and a full refill on arriving in town (a death lands there too). A death stops a heal in progress.
- It lives in `GameSession.Potion` (its changes raise `Modified`), so charges carry across scenes and deaths and are saved (save format 3; a version 2 save loads with full charges).
- `AutoPotionDirector` (created from code, kept across scenes) counts kills from each scene's `EnemyManager`, ticks the potion with scaled time (so the inventory pause stops the heal) and applies it through `PlayerHealth.Heal`, calling out a green "POTION" above the player through `DamageNumbers.ShowText`.
- HUD: `PotionPips`, one square per charge right of the life bar, filling bottom-up with kill progress. `SurvivalSceneBuilder.AddPotionPips` is idempotent and was used on the existing HUD, like the XP bar.

## Settings

- `GameSettings` (pure, tested) holds the player's settings: stick size (48 to 96 points, 64) and dead zone (4 to 20 percent, 8), handedness, the auto-potion threshold (20 to 60 percent, 35), music (80) and effects (100) volume, reduce flashing and reduce motion. Only settings with a decided source and a built system (Docs/06's table is a proposal); the others wait. `Clamp` snaps every value to its range and step, so a hand-edited or newer file cannot push a value the systems do not expect.
- `SettingsDirector` (created from code before the first scene, kept across scenes) loads them from the account file (`<persistentDataPath>/Save/account.json`, Docs/07's shared file, through `SaveStore` with the save's own rules: atomic write, 3 backups, fallback; `SaveStore.TryLoad<T>` is the general form of `Load`) and hands them out as `SettingsDirector.Current` (never null) with a `Changed` event. `Apply(copy)` sets new ones and writes them 0.5 s later (unscaled time), or at once when the app goes to the background. It saves only when `SaveDirector.Enabled`, so in the editor settings last one play unless Save In Editor is ticked. Its statics reset at `SubsystemRegistration`, before any object subscribes at `BeforeSceneLoad` (`TravelDirector` does).
- Read at the point of use, not cached: `FloatingStickInput` (radius, dead zone), `AutoPotionDirector` (sets the potion's `TriggerFraction` each frame), `MusicDirector` (`FullVolume` 0.375 times the setting, so 80 is the old 0.3; it keeps running after the fade so a change is heard at once), `Sfx` (scales every voice), `FollowCamera` (no lead with reduce motion), `HitStop` (none with reduce motion), `BossBar.Flash` (reduce flashing: a quarter as bright, rising and falling over 1.2 s). `Handedness.PlaceInCorner` mirrors the Bag button (`InventoryScreen`) and the Portal button (`TravelDirector`) into the lower left corner on `Changed`.
- `SettingsScreen`: a Settings button in the Bag's top-left corner opens a bottom sheet (sort order 55) grouped Controls, Combat, Audio, Accessibility, with − and + steppers and on/off chips, 56 points each; the Bag closing closes it. Checked in play mode on 2026-09-28 through its own buttons (handedness moved the Bag button, the potion took 40 percent, the stick grew, the music followed) and on the simulator (it opens and renders; injected taps could not work its rows, see Builds and performance).
- Reset (the owner, 2026-09-29): Settings' bottom row is Close and Reset save, which asks a second tap ("Tap again to erase") and calls `SaveDirector.StartOver`: the save files are set aside as `*.reset-<time>`, not deleted, a new `GameSession` is installed, the save director moves to it and the town loads (the travel and onboarding directors already re-read the session on each scene load). ## Progression

- `Experience` (pure, tested against the table in `Docs/04-progression-and-economy.md`): XP to the next level is 400 times level^2.2, a normal enemy is worth 8 times level^1.5, Elites 8 times that. Full XP within 3 levels either way; beyond that 12 percent less per level further below (down to nothing) and 8 percent more per level further above (up to 150 percent). The steps count from the edge of the band (4 below gives 88 percent), the user's decision. Champions give 3 times normal XP, like their gold (the user asked for more than normal; 3 is a tuning value).
- `CharacterProgress` (pure, tested) holds the level (1 to 60) and the XP toward the next level, carrying the remainder over, several levels from one grant if need be. At level 60 XP stops counting; the docs send it to Paragon, which is not built.
- Stand-in Vitality (`CombatFormulas.CharacterLife`, used by `PlayerHealth`, `PowerScore` and the inventory stats): 8 Vitality points per level from level 2, 8 life each (Docs/02), so 64 life a level on top of Docs/03's base life, until the passive tree exists (the user's decision of 2026-09-26; the amount is Claude's, picked with the balance report).
- `GameSession.Progress`/`Level`/`GrantExperience`: a level up refills life (the user's decision, as in Diablo 1: `LifeFraction` goes to 1 and `PlayerHealth` follows on `LeveledUp`), raises `Changed` (max life follows `CombatFormulas.CharacterBaseLife(level)`) and then `LeveledUp`. Level only raises max life so far. Passive points, skill points and skill unlocks from the docs' level rewards are not built.
- `ExperienceDirector` (created from code, kept across scenes, subscribes to each scene's `EnemyManager.Killed` on load) grants the XP and calls out "LEVEL n" above the player through `DamageNumbers.ShowText`. The docs' level-up sound and passive point badge wait for audio and passives.
- HUD: a thin gold `ExperienceBar` under the life bar and the level number left of it. `SurvivalSceneBuilder.BuildHud` builds them; `SurvivalSceneBuilder.AddExperienceBar` is idempotent and was used to add them to the existing Sandbox and Town HUDs without rerunning the build chain. The inventory screen's stats show level and XP.
- Verified on the simulator on 2026-09-23: a version 1 save loaded as level 1 and was rewritten as version 2; clearing the Sandbox's Elite pack and about 21 normals gave level 2 with 24 XP over (424 of 400, exactly as the formulas say), and a kill 4 XP short of level 4 showed the gold "LEVEL 4" callout and updated the HUD.

## Saving

- Follows the save system in `Docs/07-technical.md`: one JSON file per character (`<persistentDataPath>/Save/character.json`), written atomically (temporary file, flushed, then renamed), with the last 3 versions kept as `.bak1` to `.bak3`, newest first. There is no account file yet, since nothing shared across characters (stash, settings) exists.
- `SaveData` (the file's records; enums stored by name so adding or reordering an `ItemSlot`/`AffixId` cannot corrupt a save), `SaveCodec` (session to data and JSON and back, plus the migration steps) and `SaveStore` (file rules, backups, fallback) are pure and tested, `SaveStore` against a temporary directory. Saved: equipment, backpack, gold, life, level and XP, potion charges, corpses, killed pack members, opened chests, the dungeon seed and the bad-luck counter. Not saved: the loot generator's own state (a loaded session reseeds it) and drops still on the ground (already lost on any scene change).
- Schema: `SaveData.CurrentVersion` (8; version 2 added level and XP, 3 potion charges, 4 the dungeon seed and opened chests, 5 the dungeon generator version, 6 salvage materials and each item's reforge and temper counts, 7 onboarding and play time, 8 waypoints, the Portal Tome and an open portal; each migration has a test that loads an old file). A save from a newer build is refused rather than half-read. When the shape changes, bump the version and add a step to `SaveCodec.Migrations` with a test that loads an old file. Unknown item slots, rarities or affixes are dropped with a warning; the rest loads.
- Bad reads: the store tries the main file, then each backup, and logs which one it fell back to. When nothing is readable, `SaveDirector` renames every file to `*.unreadable-<time>` before starting a new game, so no save a later build could still read gets written over. Only logged so far; the docs' "reports which one it loaded" has no UI yet.
- `SaveDirector` (created from code before the first scene, kept across scenes) loads the save and writes it 2 s after the first unsaved change (`GameSession.Modified`: gold, pickups, equipping, discards, kills, deaths, corpse retrieval; life is left out because it changes every hit), and at once on a scene change, a death (`DeathFlow` calls `SaveDirector.SaveNow`, so killing the app during the fade cannot undo a death) and the app going to the background or quitting. A write failure is logged and the game carries on.
- A loaded game restarts in town (the user's decision, logged in `Docs/08-production.md` and `Docs/07-technical.md`); the position in a level is not saved. It works because the town is the first build scene.
- In the editor saving is off unless `Tools > ARPG > Save > Save In Editor` is ticked (an EditorPref), so play-testing the Sandbox does not find its packs already dead. The same menu has Delete Save and Show Save Folder. Device and simulator builds always save.
- Verified on the simulator on 2026-09-23: fought in the Sandbox, died, then `kill -9` on the app. The relaunch restored gold, the kills (those enemies stayed gone) and the corpse, with the character unarmed; a second, unarmed death added kills and left the first corpse in place.

## Lighting and effects

- Docs/05: dark scenes lit by the player's ember and enemy effects, 2D lights on the player and a few props only. `LightingDirector` (created from code, kept across scenes) sets the scene's global `Light2D` on load: the dungeon near black and cool (0.2), the town at dusk (0.62). A scene that is neither (the Sandbox) stays fully lit. It adds a warm flickering ember point light to the player (outer radius 9 world units, past the aggro range) and a flickering light at the Forge. `WorldLights` adds the prop lights, only in a dark scene: stairs (`SceneExit.Awake`, which covers a boss's stairs appearing mid-level), waypoints, the Waystone and portals (their `Create`). Numbers in `LightingRules` (pure, tested); all are tuning.
- A URP point light is a circle on screen whatever its transform's scale (`Light2D.GetMatrix` uses the radius alone), so a pool reaches further in ground units up and down than sideways. Squashing the transform does nothing.
- Everything that must read in the dark is unlit: `GroundMarker.NewSprite` (telegraphs, fire, arrows, thrown axes, travel rings), `SweepEffect` and `LootDrop` beams and markers use `SpriteMaterials.Unlit` (`Resources/Materials/SpriteUnlit.mat`). Characters, walls, floors, chests and NPC figures stay on the lit default material. `TextMesh` labels and all UI ignore 2D lights.
- `SpriteEffects` (plain class, ticked by its owner) does a hit flash and a death dissolve by swapping a character's body renderers to `Resources/Materials/SpriteEffect.mat` (shader `ARPG/Sprite Effect` in `Shaders/`, unlit, darkened by `LightingDirector.CharacterShade`) with a property block, and back to their own material afterwards. Enemies flash white for 0.1 s on every hit and burn away over their death time (0.45 s now, from 0.25, so the dissolve can be seen) while the shadow fades; the player flashes red when hit. The shadow renderer is left out of both.
- Floor variation: `WorldLights.ShadeGround` tints every ground tile by `LightingRules.FloorShade(cell)` (brightness 0.82 to 1, a touch warmer or cooler, a stable hash). `DungeonLevel.Paint` calls it; the director does the town's Ground tilemap on load.
- Shadows under characters were already there (a shadow ellipse child on the player and enemy prefabs). NPC figures (`TravelArt.Figure`) got one.
- `Tools > ARPG > Create Lighting Materials` (`LightingSetup.cs`) creates the two materials if missing. `ARPG.Runtime` references the URP runtime assemblies (`Light2D` is in `Unity.RenderPipelines.Universal.2D.Runtime`).
- Checked with game-camera captures in play mode on 2026-09-26 (dungeon, a fight with flashes and a dissolve, town), not yet on the simulator or a device.

## Sprite bake (3D models to sprite sheets)

- Docs/09-art-brief.md, Route A and 4.5: characters are rendered from 3D models into frame sheets. `SpriteBaker` (editor, `Scripts/Editor/SpriteBake`) bakes a `SpriteBakeJob` asset (Assets > Create > ARPG > Sprite Bake Job): one or more **bodies** (the whole figure in one chest look, all sharing the first body's proportions), optional **pieces** (helm, off-hand or weapon: a rigid model on a humanoid bone or a transform path of the first body, baked for the grips it lists), and a **clip set per grip** (1h, dual, shield, 2h), plus cell size, feet pivot, target height in pixels, supersampling and output folder. `Tools > ARPG > Sprite Bake > Bake Selected Jobs` runs it.
- For every grip, clip and layer (each body, each piece for that grip), direction and frame: the bodies are posed through a `PlayableGraph` each (humanoid or generic clips, no root motion, rest pose restored before each frame, since a generic clip leaves unanimated bones where the last clip put them: the first test attack ran on frozen running legs), turned to the direction and rendered orthographically at the game's 30 degree camera (one tile's 1 m diagonal is 128 px; `SpriteBakeMath`, pure, tested). A body is rendered alone; a piece is rendered with the first body drawing depth only (`Shaders/DepthOnly.shader`, editor use only), so the piece comes out cut wherever the body hides it and the game can stack layers with no draw-order table. Pieces do not cut each other (a weapon passing behind a helm draws over it). Each frame is rendered at the supersampling over black and over white, the transparency recovered from the difference (`SpriteBakeMath.Matte`; the project's HDR drops the camera's alpha), averaged down by coverage, converted to sRGB, and written in the brief's layout: rows S, SW, W, NW, N, NE, E, SE from the top, frames in columns; a sheet over 4096 px becomes one file per direction (`<name>_<dir>.png`, rows of 8 for 512 cells). Sheets are named `<character>_<layer>_<look>_<grip>_<clip>` (`AppearanceRules.SheetName`; a plain character with one unnamed body and no pieces or grip names gets `<character>_<clip>`), imported as sliced sprites named `<sheet>_<dir>_<frame>`, pivot at the feet, 128 pixels per unit; a rebake keeps sprite ids by name. Real characters go to `Assets/_Project/Resources/Characters/<character>`, where the game loads them.
- The project renders with the 2D renderer, which draws 3D meshes flat. The bake adds `Assets/_Project/Settings/SpriteBakeRenderer.asset` (a Universal renderer) to the pipeline asset's renderer list for the length of the bake, gives it to its camera, and removes it after, so the build does not carry it. The scene is a preview scene, so open scenes are untouched. Lights turn with the camera: key from the viewer's upper left, a cool fill from the right, a rim from behind, no shadows. The first render after adding the renderer came out unlit, so one is thrown away first.
- The first body is scaled so its rest pose (bounding box height and depth, seen from the front) shows `targetHeightPixels` tall; the others get the same scale and placement. The single-model mannequin (1.9 m) came out 164 px against a target of 170, because the box counts depth the body does not fill. Feet pivot at (128, 40): toes nearer the camera reach a few pixels below it, which is right for this view.
- `Tools > ARPG > Sprite Bake > Bake Test Mannequin` (`SpriteBakeTestRig`) builds a primitive mannequin with a generic rig (a red nose on the face and the lantern on its left side, to catch a wrong direction or hand) in four body looks (bare, padded, leather, mail), three helms, three one-handed axes, a two-handed great axe, an off-hand hatchet and a shield, with an idle, a run and an attack made in code for each grip, and bakes them at 2x into `Assets/_Project/Art/SpriteBakeTest/Resources/Characters/mannequin` (git-ignored). **A Resources folder goes into the build**: run Delete Test Mannequin (same menu) or remove that folder before building. The Unity MCP bridge refuses `AssetDatabase.DeleteAsset`, so from a command remove it with the shell. Checked on 2026-09-27: 120 sheets in 259 s; in the Sandbox with `PlayerSpriteAnimator.Character = "mannequin"`, equipping a level 8 chest and helm and a level 5 weapon swapped the stack from bare body and hatchet to mail, great helm and bearded axe; all four grips showed their off-hand and weapon layers mid-attack, cut behind the body where they should be.
- Lessons from the first real model (the Wrathborn, 2026-09-27): a `PlayableGraph` evaluated in the editor leaves a humanoid in its bind pose, so the bake poses with `AnimationClip.SampleAnimation` (humanoid and generic alike) and puts the root back after, so a clip not downloaded In Place stays on the spot. A skinned mesh is re-skinned once per editor frame, not per camera render, so rendering it right after posing drew the rest shape carried rigidly by the hips (a run with no running): the bake draws a stand-in `MeshRenderer` baked from the skinned mesh each frame (`SkinProxy`). Bones can look fine while the mesh is wrong: check a rendered sheet, not a bone position. Mixamo's re-export does not bring the texture into Unity, so `ArtSource/tools/extract_textures.py` takes it from the image-to-3D GLB (`<body>_albedo.png` beside the FBX) and the setup puts it on a URP material that replaces the model's. Mixamo clips vary in length (the Breathing Idle is 9.9 s, the run 0.7 s), so each sheet plays over its clip's real length: the bake writes `<character>_timing.txt` (`<grip>_<clip> <seconds>`) and `LayeredCharacterSprite` reads it.
- `Tools > ARPG > Sprite Bake > Set Up Wrathborn` / `Bake Wrathborn` (`WrathbornBakeSetup`): reads `Assets/_Project/Art/Models/Wrathborn`, where bodies are `wrathborn_body_<look>.fbx` (with skin; its own clip is the 1h idle) and animations `wrathborn_<grip>_<animation>.fbx` (without skin), sets humanoid rigs (animations copy the leather body's avatar), in-place clips, loops and the textured material, and writes `WrathbornJob.asset` with the brief's frame counts (the idle 24, since Mixamo idles are long) into `Resources/Characters/wrathborn`. Rerun after adding files. The axe is not modelled yet, so he fights empty-handed. `AppearanceRules.FallbackLook` shows the leather body and the bearded axe when a look has no sheets yet (a new character wears no chest, whose bare body is not made yet).
- Weapons (2026-09-27, the bearded axe): `ArtSource/tools/prepare_weapon.py <in.glb> <out.fbx> <length_m> <grip>` scales an image-to-3D weapon (standing, head up) to its real length and puts the grip (a fraction up from the butt, on the haft's centre line) at the origin; the axe is 0.75 m, grip 0.18. `WrathbornBakeSetup` turns each `wrathborn_weapon_<look>.fbx` into `<...>_held.prefab`, textured from `<...>_albedo.png`, turned so the blade faces +Z (read from the mesh: the blade holds the mass off the haft), and adds it as a right-hand piece for the 1h, dual and shield grips. `SpriteBakeJob.Piece.autoGrip` places it from the hand's bones in the rest pose (`SpriteBaker.PlaceInFist`: the haft from the little finger to the index, head on the thumb side; the blade the way the fingers point; the grip 0.6 of the way from the wrist to the middle knuckle) at the body's scale, whatever scale the hand bone carries.
- A bug the axe exposed (2026-09-27): `SkinnedMeshRenderer.BakeMesh(mesh, true)` with the renderer's position and rotation drew the body 1.55 times too big at the bake scale of 0.645, grown around the wrong point, so a held axe hung 25 cm off the hand it was fixed to and the body came out about 200 px tall. ## Gear on the character

- Decisions of 2026-09-27 (Docs/08, Docs/03 Appearance, brief 4.5): gear oriented like Diablo 2, equipped gear is displayed on the character. Shown slots: weapon, off-hand, helm, chest (the chest sets arms and legs). Looks in tiers by item level (act 1: 1 to 3, 4 to 6, 7 and up) plus a unique model per legendary (not possible yet: no named legendaries exist, so a legendary shows its tier). The off-hand holds nothing, an off-hand weapon or a shield, or a two-handed weapon takes both hands; each grip has its own animation set.
- `AppearanceRules` (pure, tested) turns `EquipmentState` into a `CharacterAppearance`: a look id per layer (`bare` body and null helm, off-hand and weapon when empty) and a `CharacterGrip`. The off-hand slot and two-handed weapons are not items yet, so the game's grip is always one-handed; `GripFor` is the rule for when they are. `DirectionRow` maps a ground direction to the sheet row the bake rendered facing it (tested against `SpriteBakeMath.Facing`).
- `LayeredCharacterSprite` draws body, helm, off-hand and weapon as four sprite renderers in one `SortingGroup` on the Entities layer, loading each sheet from `Resources/Characters/<character>/<sheet>` on first use (a split sheet as its eight files) and, when the look changes, dropping them all and calling `Resources.UnloadUnusedAssets`, so only equipped looks stay in memory. That call also destroys a runtime-created object held only by a local variable (it took a test's capture texture); objects held by components or statics are safe. Frames play at 12 fps; the sheets of the playing animation are looked up when the animation or look changes, so a frame allocates nothing.
- Sheets load with the look, not on first play: `LayeredCharacterSprite.SetAppearance` preloads every animation the player can play (idle, runs, Bull Rush, hit, death, the four actions and their moving variants) for every layer. Loading one the first time it played cost about 50 ms in the editor and froze the phone when a big pack was engaged (the owner, 2026-09-29); the worst frame of a 10 husk fight went from 55 ms to 9.5. `CharacterPortrait` (the HUD's, refreshed on every `GameSession.Changed`, so every kill and gold pickup) reloads only when the look changes, and caches its frames.

## Notes

- Stepping play mode from a script: with the editor in the background, play mode can stop advancing frames entirely (`Time.frameCount` stays put between commands), which leaves anything updated in `LateUpdate` stale (a teleported `Light2D` kept its old culling sphere and vanished). Pause, set `Time.captureDeltaTime = 1/60f`, and call `EditorApplication.Step()` in a loop: it runs frames synchronously. Render `Camera.main` to a RenderTexture and save a PNG for a game-view capture (the capture tool's camera id wants `GetInstanceID`, obsolete in Unity 6). Reset `captureDeltaTime` to 0 afterwards.
- Game-view captures with the Pixel Perfect Camera: `RenderResolution` adds it to the main camera in play mode, and it sets the camera's orthographic size and pixel rect from `Screen`, which in the editor is whatever the Game view is (2940 x 72 once, with the editor in the background), so a capture rendered by hand came out as the whole map, tiny. Disable the component, set `camera.rect` to the full rect and the orthographic size to 7.5 before capturing.
- Measuring allocations in the editor: `GC.GetAllocatedBytesForCurrentThread()` always returns 0 here, even for a 100 KB array, so it proves nothing. `Profiler.GetMonoUsedSizeLong()` and `GC.GetTotalMemory(false)` work but move in blocks of about 4 KB, so use them over thousands of iterations (compare against a control loop) and first check that they detect an allocation you know you made. An earlier version of these notes claimed "0 bytes" from the dead counter.
- Unity only looks for changed files when its window gets focus. `BackgroundRefresh` (editor script) watches `Assets/**/*.cs` and calls `AssetDatabase.Refresh` from the editor loop, so edits made from outside recompile with the editor in the background (about 4 s; checked 2026-09-26). It waits while in play mode. Setting Preferences > General > Interaction Mode to No Throttling keeps the background editor loop at full speed. A Unity MCP command refreshes the asset database itself, so a script edited during play mode is compiled in the middle of the play session (Script Changes While Playing defaults to Recompile And Continue Playing). That reload loses runtime state such as event subscriptions and broke a running test twice. Do not edit scripts while playing, or set that preference to Recompile After Finished Playing.
- Unity holds a lock on the project while the editor is open. Do not hand-edit `ProjectSettings/*.asset` then; apply settings through editor scripts instead.

## 2026-10-13: glitchy boss walks; her "spaghetti legs"

- The owner: her run "looks really odd. Like spaghetti legs", and the bosses' walks "are really glitchy".
